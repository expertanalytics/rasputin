# Increment 30b acceptance: the `features clip` phase of `rasputin mesh`

@perf, 2026-10-06. Base: the merge commit `5e2fbe0`. Branch:
`worktree-clip-speed` at `c5340459` (the green step). The acceptance is
section 9 of `docs/increments/30b-clip-speed.md`.

**Verdict: ACCEPTED.** The branch's `features clip` median is under the
design's limit of 0.4 of the base's on both catchments (the gate table
below). Every mesh is byte-identical to the base's, and the design's probe
finds every base line unchanged.

Every figure in the tables between the `GENERATED` markers is written there by
`scripts/summarize.py` from `raw/stats/`; none is copied by hand. Rerun it to
check them.

## Method

- **Machine:** Apple M1 Max (8 performance and 2 efficiency cores), 32 GB,
  macOS 27.0. Python 3.13.15, numpy 2.5.3, shapely 2.1.2 with GEOS 3.13.1, on
  both sides. 10 threads.
- **Power: AC for every run.** `pmset -g batt` was read before and after each
  run (`raw/stats/*_power.txt`, `raw/probe_power.txt`). The bottleneck
  profile in `../bottlenecks/` was made on battery, so it is not compared.
- **Installs**, both non-editable, each checked before the runs:
  - base: the worktree's `.venv`, installed from the tree at `5e2fbe0`. Its
    installed `tin_engine/*.py` files equal `git archive 5e2fbe0
    src_python/tin_engine` file for file (`diff -rq`, no differences).
  - branch: a scratch venv, `uv pip install ".[codecs]"` from `git archive
    c5340459`. Its `tin_engine/*.py` files equal `git archive c5340459
    src_python/tin_engine` file for file.
  - The only source difference between the two is
    `src_python/tin_engine/feature_input.py` (`git diff --stat 5e2fbe0
    c5340459 -- src_python include src CMakeLists.txt pyproject.toml`).
  - Both load a `_core` extension with the same sha256 (`5b0adf95…`), a
    Release build with bounds checks on (libc++ fast mode), as each stats
    file says. So build mode and hardening are the same on both sides.
- **Command:** `scripts/stats.sh <side> <catchment> <repeat>`, driven by
  `scripts/run_all.sh`: `rasputin mesh` with DEM
  `rasputin_data/DTM10_UTM33_20260925`, domain
  `rasputin_scratch/norway/<c>/<c>_outline_nve.geojson`, `--features
  rasputin_data/corine2018_dtm10_utm33.gpkg --features-layer corine2018
  --features-map corine --tolerance 10 --binary --stats`. The inputs and
  flags are those of the bottleneck profile and of 30a's acceptance.
- **Repeats:** 3 per catchment per side, base and branch alternated: base
  first on odd repeats, branch first on even ones. Nothing else ran during
  the timing runs. The tables give the median.
- **Byte-identity:** the sha256 of every `.vtk` the 12 timing runs wrote
  (`raw/stats/vtk_sha256.txt`). Then the design's probe
  (`docs/increments/30b-probes/clip_bytes.py`), run on the branch install
  after the timing runs, in `fixtures` mode and `mesh` mode
  (`scripts/probe.sh`), and compared with
  `docs/increments/30b-probes/base_5e2fbe0.txt` by section 6's two `comm`
  commands (`raw/probe_compare.txt`). The comparison was checked once by
  planting a changed `vtk=` value in a copy of the base file: the first
  `comm` printed that line.
- The meshes (about 58 and 134 MB each) are not committed. They were written
  to the session scratchpad. To regenerate them, set `S=` in
  `scripts/stats.sh` and rerun `scripts/run_all.sh`; the branch venv is
  rebuilt with `uv venv` and `uv pip install ".[codecs]"` in a `git archive
  c5340459` tree.

## Probe

`raw/probe_compare.txt`: no base `fixture` or `mesh` line is missing or
changed on the branch. The branch has 11 `fixture` lines the base lacks, all
from `test_feature_input.py::TestTheClipStaysTheSame` (P1's four cases, P3's
one test, P4's three cases, P5's three cases), which is the list section 6
allows. The `fixtures` run's pytest exited 0 (`raw/probe_fixtures_branch.txt`,
last lines). Both probe `mesh` lines, `.vtk` hashes included, equal the base
file's.

Quality is the same on both sides because the meshes are byte-identical (the
quality table above is read from the stats files). The Delaunay check is not
part of `mesh --stats` and was not run separately, for the same reason.

The `features read` row and the total are recorded, not gated. The read row
moves within its spread between repeats, as section 9 predicts for an
unchanged read. The total falls by about the clip saving; the other phases
were not compared row by row.
