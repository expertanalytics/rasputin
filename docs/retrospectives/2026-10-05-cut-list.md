## 3. The cut list

Ranked by what it saves in time first, then in words. Words are estimates
from `wc -w` on the passage, net of any replacement sentence; they are not
measured after an edit. "Risk" is what can come back.

### Protocol steps (time)

**P1. The review record is one line per round.** Verdict, commit range, net
lines, and the blocking items as a list; the rest of the handback is not
copied. This is what the README already says; the cut is to stop doing more.
Saves: about one `@architect` spawn and one commit per review round (33 to
61 record commits a day), and it stops increment files growing by
thousands of words that every later spawn reads. Removes: the word-for-word
practice of 3fab6c6 and after. Risk: a suggestion that was not blocking is
lost when the transcript goes; the handback file can be kept untracked in
the worktree until the merge.

**P2. No design review round by default.** `@reviewer` reviews once before
the first push, as `REQUIRED-READING.md` says; a design is reviewed only
when Ola asks or when it changes CI or a guard. Saves: h12 spent four
design rounds (00:48 to 01:16 today) before its red step. Risk: a design
defect is found after code exists, costing a red-green loop instead of an
edit.

**P3. `@tester`'s pinned choices are accepted unless they change an
interface.** Today `@architect` confirms each choice before green
(`tester.md` §1, "Choices beyond the design"); 29 PR 4 had a spawn for it
(04:05, "tester's red-step choices adopted"). `@reviewer` reads the list at
review instead. Saves: one spawn per increment, about 20 words of rule.
Risk: a choice the architect would have changed is caught one step later.

**P4. Questions for Ola are batched once per increment, not per round.**
About 28 ruling-record commits since 3 October, several for one or two questions.
`@architect` keeps the defaults and records all rulings in one commit before
the push. Risk: a wrong default runs a little longer before Ola sees it.

**P5. Retrospectives land weekly, in one PR.** Each of the last three had
two review rounds and its own CI run. They are committed on one branch and
pushed once a week. Risk: a lesson waits days to reach `master`; the rule
changes that come from it wait for Ola anyway.

**P6. CI.** h12 PR A's queue skip and h15 (CI split) are the CI-speed work
Ola asked for; both should land before the freeze, and nothing else in CI
during it.

## 4. Is this a known pattern?

Yes. Practitioners and Anthropic say the same thing.

- Thoughtworks Technology Radar (vol. 34, April 2026) lists "agent
  instruction bloat" under **Caution**: context files "accumulate over time
  as teams add codebase overviews, architectural explanations, conventions
  and rules", grow long and contradict each other. Advice: "continuously
  refine toward a minimal, coherent set", and show an agent only what its
  task needs.
- Claude Code's documentation: "target under 200 lines per CLAUDE.md file.
  Longer files consume more context and reduce adherence." Here a spawn
  reads `CLAUDE.md` (130 lines), `REQUIRED-READING.md` (204), the increments
  README (133), its persona file, and the increment file (3,349 lines for 29).
- Anthropic, *Effective context engineering for AI agents*: aim for "the
  minimal set of information that fully outlines your expected behavior",
  and do not stuff "a laundry list of edge cases into a prompt". Most rules
  here were added after one incident each.
- Anthropic, *Building effective agents*: add complexity "only when it
  demonstrably improves outcomes". No rule here has been measured for what it
  prevents against what it costs.
- Jaroslawicz et al. 2025, *How Many Instructions Can LLMs Follow at Once?*
  (arXiv 2507.11538): adherence falls as the number of instructions grows;
  the best models reach 68 % at 500 instructions.
- METR's 2025 trial: experienced developers took 19 % longer with AI tools
  while believing they were 20 % faster. The lesson for us: measure speed
  (section 1), do not judge it by feel.
- Cognition (Walden Yan, June 2025), *Don't build multi-agents*: "running
  multiple agents in collaboration only results in fragile systems"; share
  full context rather than messages. The record-keeping steps here exist to
  move context between agents; P1 to P4 cut the hand-offs, not only the text.

What they recommend: fewer, shorter rules; checks in code (hooks, tests)
rather than prose; delete a rule when a check covers it; measure.

## 5. Lessons from today (passed by the main session)

1. **`tools/brief.py` named two briefs' note files alike.** The name is
   `<persona>-<HHMMSS>.md` (`brief.py`, `strftime("%H%M%S")`), so two briefs
   for one persona in the same second collide. h16 PR A's red step covers it
   ("brief.py note names", 10:24).
2. **`brief.py` counts verdict lines, not rounds.** It counts every line in
   a `## Review` section that contains `APPROVED` or `CHANGES REQUESTED`
   (`tools/brief.py`, the `rounds =` line), so a word-for-word record with the
   verdict in several lines printed "Review rounds recorded: 4" on a file
   with 3. P1 also removes the cause.
3. **`guard_spawn.py` refused a pasted brief with a duplicated line.** It
   worked as intended: the block must be unchanged.
4. **`@tester` wrote throwaway implementations** although lean briefs (no
   throwaway or mutation rounds unless the increment file names a suite
   invariant-critical) are the default. `tester.md` §4 asks for a scratch
   run of a fix the design names by location; the persona read that as
   licence to write one. Proposal: `tester.md` says that run uses a fix
   that already exists, never one `@tester` writes.
5. **`@developer` ran `git stash` on the shared worktree to check red**; it
   left the tree clean. `tools/scratch_copy.py` (h16 PR A) is the route that
   does not touch the worktree; brief `@developer` to use it once merged.
6. **A governed-file edit cannot finish in an unattended step.** h16's
   `brief.py` change went to `@developer` while Ola was away; the guard
   refused it, as it should. The queue should not give an unattended window
   a step that writes `tools/`, `.claude/` or a rule file.
7. **A design claim about CI was true of a different job.** h16's design
   said a full clone was in place; it held for another job, and the Python
   job needed `fetch-depth: 0` (h16 PR A green, 11:46). The design claim
   rule (`REQUIRED-READING.md`, *Claims*) applies: name the job the claim is
   about.
8. **The main session called a term Ola's that he did not know.** It passed
   "root-file limit" to a persona as if Ola had used it. A label coined by an
   agent is not Ola's; only text under "Ola, verbatim" is.
